## 2. Is the origin story verifiable, and what do independent sources say?

### Takeaway
The "740 listings evaluated, 68 applied, 12 interviews, 1 offer" funnel is **self-reported and not independently verifiable**. The employer is never named, the author's own page has internal inconsistencies, and secondary sources variously say 66 or 68 applications. There is substantial launch coverage, but almost no independent hands-on review. Hacker News traction is negligible. Criticism centres on token usage, the original "740 offers" wording, and the AI-centric defaults.

Evidence offered is screenshots (tracker, a Datadog evaluation scored 4.55/5, CV/cover letter samples) and a score distribution. **Inconsistencies**: the hero image alt text says "516 evaluated offers", and the score distribution (21/52/71/51) sums to 195, not 740 — [santifer.io/career-ops-system](https://santifer.io/career-ops-system)

## 3. What it does end to end, and how heavy it is to operate

### Takeaway
It is a full job-search operating system run as agent instructions plus Node scripts. Features: portal scanning, A–G evaluation reports with a 1–5 score, tailored CV (HTML→PDF or LaTeX), cover letters, a tracker, follow-ups, outreach drafts, interview prep, offer review and analytics. It is **heavy**. Measured with the repo's own estimator, one interactive evaluation loads about 49k tokens of instructions before the CV or JD, and the project's own budget doc understates this as about 26k.

### Cited Findings
- package.json description: "Open-source AI job search that runs locally in your AI coding CLI: scan job portals, evaluate listings into a structured A-H report with a 1-5 score, tailor your CV, track applications" — `/home/user/career-ops/package.json`. The GitHub description adds "It helps you fill in each application; you press Submit" — [repo](https://github.com/career-ops-hq/career-ops)
- Modes listed in AGENTS.md: auto-pipeline (evaluate + report + PDF + tracker), oferta/ofertas (evaluate/compare), contacto (LinkedIn outreach drafts), email (draft-only), deep (company research), interview-prep / interview plan / practice / debrief, interview-redflag, pdf / latex / text / ats, cover, add, expand, training, project, tracker, apply (form filling, never submits), scan, discover, pipeline, triage, batch, patterns, calibrate, offer-prep, titles, upskill, intake, retro, followup, reply-watch, outcome, update, agent-inbox — `/home/user/career-ops/AGENTS.md` ("Skill Modes" table)
- Reports carry Blocks A-F + G (Posting Legitimacy) + Verdict + Risk Summary + a `## Machine Summary` YAML, and must archive the JD verbatim — `/home/user/career-ops/AGENTS.md` (Main Files table; "JD archival is REQUIRED")
- **Size**: 155 top-level `.mjs` scripts, 45 mode files at `modes/` root plus 25 subdirectories (20 of them language/market sets), 112 scanner provider modules, 814 test files. AGENTS.md alone is 686 lines and 84,749 bytes — `ls`/`wc` in `/home/user/career-ops`
- **Instruction-token floor (measured 2026-10-22 with the repo's `lib/context-budget.mjs` `estimateTokens`)**: AGENTS.md 20,965 + `modes/_shared.md` 7,301 + `modes/oferta.md` 20,608 = **≈48,900 tokens** per interactive evaluation. Other modes: pdf.md 12,487; apply.md 12,583; scan.md 9,641; auto-pipeline.md 3,010; the Claude skill router SKILL.md 4,482 — computed from `/home/user/career-ops/lib/context-budget.mjs`
- The project's own budget doc says "the agent loads AGENTS.md (8,285) + modes/_shared.md (4,127) + modes/oferta.md (13,601) = about 26,000 tokens of instructions per evaluation". **That is stale**: AGENTS.md has grown about 2.5× since that figure. The same doc says the standalone script path costs about $0.003 per evaluation at DeepSeek V3 prices, and that "Batch beats pasting" — `/home/user/career-ops/docs/RUNNING_ON_A_BUDGET.md` lines 419–453
- Cost controls: `spend_tier` economy/standard/premium in `config/profile.yml`. Research is capped at five queries with no subagents after issue #1235 — `/home/user/career-ops/docs/RUNNING_ON_A_BUDGET.md`
- Model-agnostic alternatives exist: OpenRouter, Gemini, Ollama and OpenAI eval scripts (`openrouter-runner.mjs`, `gemini-eval.mjs`, `ollama-eval.mjs`, `openai-eval.mjs`) — `/home/user/career-ops/package.json` scripts; repo root listing
- **Anti-fabrication machinery**: Source-of-Truth Boundary ("Keywords get reformulated, never fabricated"), the authorship-claims rule, story-bank provenance markers (`story-provenance-check.mjs`), and a fact gate `verify-cv-facts.mjs` that checks generated CVs and documents against `cv.md`/`article-digest.md` — `/home/user/career-ops/AGENTS.md`; `/home/user/career-ops/verify-cv-facts.mjs`. Open issue #5632 shows that gate can raise false positives — [Issues](https://github.com/career-ops-hq/career-ops/issues)

### Inferences
- For one user evaluating a handful of roles a day on a Claude subscription, the roughly 49k-token floor is affordable. Claude Code caches the static prefix within a session. It does consume context window and usage limits quickly in long "paste URL after URL" sessions, though, which echoes the top Reddit concern.
- The breadth (40+ modes, 155 scripts) is both strength and burden. Most value for this user is in a small subset: onboarding, oferta/auto-pipeline, pdf, cover, tracker, interview-prep, followup and scan with API providers. Much of the rest (US/DACH/Asia-specific signals, 20 language sets, a Go dashboard, a web alpha) is irrelevant weight that still loads via AGENTS.md.

### Gaps
- No measured real-world token or $ cost per evaluation inside Claude Code (with caching) was found from an independent source. The figures above are instruction-size floors only.

## 4. Fit for cloud-only use (Claude Code on the web) and persisting personal data

### Takeaway
It works in a cloud session, but with friction the project itself documents. Its own SETUP.md says **not to use a public fork for personal data** and that gitignored personal files **do not persist** between cloud sessions. PDF generation works if Chromium is reinstalled each session (verified). Live form-filling in apply mode does **not** work in the cloud: it requires a headed browser (verified failure). The supported data-root override (`CAREER_OPS_DATA_DIR` / `.career-ops-data`) makes a **separate private "data" repo** a workable design, provided it is committed and pushed every session.

### Cited Findings
- The project's own cloud guidance ("Browser-only — Claude Code on the web"): "Put career-ops in a **private GitHub repository**... You can use GitHub Importer... A normal fork of this public repository is public, so do not use one for personal career data." Also: "`cv.md`, runtime content under `data/`, and Markdown files directly under `reports/` are intentionally git-ignored... a normal web-session branch push does **not** persist them to GitHub: a new cloud session starts from the repository again, without the ignored files from the previous VM... Never force-add these paths. For a durable workspace shared across many sessions, use the local quick start" — `/home/user/career-ops/docs/SETUP.md` lines 11–46
- The user's fork `realsanket/career-ops` is `"private": false, "visibility": "public", "fork": true, "parent": "career-ops-hq/career-ops"` — GitHub API `repos/realsanket/career-ops` (2026-10-22)
- `.gitignore` excludes `cv.md`, `config/profile.yml`, `portals.yml`, `modes/_profile.md`, `modes/_custom.md`, `data/*`, `reports/*.md`, `output/*`, `interview-prep/*`, `jds/*`, `.env`, and the marker `/.career-ops-data` — `/home/user/career-ops/.gitignore`
- **Data-root override**: `path-resolver.mjs` uses priority "process.env.CAREER_OPS_ROOT or process.env.CAREER_OPS_DATA_DIR > .career-ops-data marker file > codebase root". DATA_CONTRACT.md says that when set, all User Layer files (`cv.md`, `config/profile.yml`, `modes/_profile.md`, `modes/_custom.md`, `data/`, `reports/`, `output/`, `portals.yml`, `batch/tracker-additions/`) resolve relative to that path, "keeping code and personal data completely separate". `CAREER_OPS_TRACKER` can override the tracker path — `/home/user/career-ops/path-resolver.mjs` lines 9–19; `/home/user/career-ops/DATA_CONTRACT.md` lines 193–209. AGENTS.md requires new scripts to resolve paths via `getCareerOpsRoot()` "because the data root can be overridden and can live outside the repository" — `/home/user/career-ops/AGENTS.md`
- `doctor.mjs` run in this cloud container reported "✗ Playwright chromium not installed", "⚠ Playwright MCP tools not detected (active CLI: claude)", and "✓ Scan extractor: mcp (default)" — `node doctor.mjs` in `/home/user/career-ops` (2026-10-22)
- **Verified in this container**: `npx playwright install chromium` downloaded Chrome Headless Shell 156.0.8078.4 (120 MiB, to `/opt/pw-browsers`), and a test `page.pdf()` produced a 5,268-byte PDF. HTML→PDF CV generation is therefore feasible in the cloud, but the install must be repeated in every new container (or scripted in an environment setup step) — local test, playwright 1.64.1
- **Verified in this container**: `node apply-scope.mjs launch-options` returns `{"headless":false}`, and `chromium.launch({headless:false})` fails with `DISPLAY` empty. Apply mode's own fallback is "If Playwright is not available, ask the candidate to paste the questions or share a screenshot" — `/home/user/career-ops/apply-scope.mjs`; `/home/user/career-ops/modes/apply.md` lines 17, 24
- Scanning: `scan.mjs` is a "Zero-token portal scanner (Greenhouse/Ashby/Lever APIs, zero LLM cost)" and needs only HTTP — `/home/user/career-ops/AGENTS.md`. But in the template, 71 of 193 portal entries use `scan_method: websearch` (agent WebSearch, costs tokens), 3 use `local_parser` and 1 uses `playwright` — `grep scan_method templates/portals.example.yml`
- Liveness: `check-liveness.mjs` uses public ATS APIs first and falls back to Playwright only when the API returns null — `/home/user/career-ops/AGENTS.md` (Offer Verification)
- The career-ops skill router is committed at `.claude/skills/` (`.agents/skills/career-ops/SKILL.md`), so a cloud session that clones the repo gets `/career-ops` automatically. It appears as an available skill in this cloud session — `/home/user/career-ops/.claude/skills`; session skill list
- Gmail exists only as an opt-in plugin (`Plugins: apify (off), gmail (off), h1b-sponsor (off), notion (off)`). There is a no-Gmail path, `paste-reply.mjs`, for reply classification — `node doctor.mjs`; `/home/user/career-ops/AGENTS.md` (paste-reply.mjs row)
- Open issue #5587 says "the no-user-data guard is not a required check" in CI. The user-data leak guard exists but is advisory — [Issues](https://github.com/career-ops-hq/career-ops/issues)

### Inferences
- **The current public fork is safe only as a code repo.** Because the personal files are gitignored, nothing private leaks *unless* someone force-adds them or a session writes personal content into a tracked file. Examples: editing a system-layer file with personal facts, or committing a generated file outside the ignored paths. It also persists **nothing** personal, so every new cloud session would start from zero.
- **The most viable cloud-only design**: keep the public fork (or better, a private import, per SETUP.md) for code. Create a **separate private GitHub repo** (e.g. `realsanket/career-ops-data`) holding `cv.md`, `config/profile.yml`, `modes/_profile.md`, `modes/_custom.md`, `portals.yml`, `data/`, `reports/`, `interview-prep/` and optionally `output/`. Each session: attach and clone it (e.g. to `/home/user/career-ops-data`), set `CAREER_OPS_DATA_DIR` (in the cloud environment's variables, or by writing the gitignored `.career-ops-data` marker at session start), work, then **commit and push the data repo before ending**. A SessionStart hook or setup script could clone the data repo, write the marker, run `npm ci` and install Chromium. Without a disciplined push, all work since the last push is lost when the container is reclaimed.
- An alternative is to make the code repo itself private (GitHub Importer, per SETUP.md) and un-ignore the personal files *in that private repo only*. That is simpler than two repos, but it contradicts the docs' "Never force-add these paths" and makes upstream updates (`update-system.mjs`) more conflict-prone. Google Drive/Docs/Sheets connectors could hold exports (PDFs, a tracker mirror) but are not native data roots.
- Losing apply-mode live form filling matters little: the user must press Submit themselves anyway. In the cloud, Claude can still draft answers from pasted questions or screenshots.

### Gaps
- Not verified end-to-end: running every script with `CAREER_OPS_DATA_DIR` pointing at a separately cloned repo in a cloud session. Some less-used scripts may still assume the repo root; open issues show path-resolution bugs being fixed incrementally.
- Not checked: whether a Claude Code web environment's environment-variable or setup-script settings persist `CAREER_OPS_DATA_DIR` and a Chromium install across sessions. The platform docs were not consulted here.
- Whether Playwright MCP can be configured in Claude Code on the web was not tested.

## 5. Finland coverage (job sources, companies, language)

### Takeaway
The scanner covers the ATSs most Finnish tech employers use (Greenhouse, Lever incl. EU, Ashby, Teamtailor, Recruitee, SmartRecruiters, Workday, Personio, Workable) plus **The Hub** (Nordic startups). It has **no** Finland-specific sources: no Duunitori, Oikotie, Jobylon, Job Market Finland/Työmarkkinatori, and no LinkedIn scanning. The template is almost devoid of Finnish companies (only Aiven), and there is no Finnish or Nordic-Finnish language mode. The user must build their own `portals.yml` company list.

### Cited Findings
- **Supported providers** (from `docs/SUPPORTED_JOB_BOARDS.md`; provider files under `providers/`):
  - Greenhouse (API, auto-detects public boards).
  - Lever (API, auto-detects `jobs.(eu.)?lever.co/<slug>`).
  - Ashby (API, plus an embed fallback).
  - Teamtailor (RSS, `<slug>.teamtailor.com/jobs.rss` or branded domain via `provider: teamtailor`).
  - Recruitee (API, with `preferred_languages` to fetch other-language translations).
  - SmartRecruiters (API).
  - Workday (CXS API, auto-detects `*.myworkdayjobs.com`).
  - Personio (parser, with language selection).

## 6. Ethics / ToS: auto-submission and LinkedIn

### Takeaway
Verified in code and docs: career-ops **does not auto-submit** applications. The submit guard is structural in the web apply driver, though it documents a residual edge case. It **does not log into or scrape LinkedIn with the user's account**. The one LinkedIn touchpoint in code is an unauthenticated, throttled call to LinkedIn's public guest job-posting endpoint for liveness checks. The ban risk to the user's account is low, but this is still automated access to LinkedIn.

### Cited Findings
- Policy: "NEVER submit an application without the user reviewing it first... always STOP before clicking Submit/Send/Apply". Below 4.0/5, "explicitly recommend against applying" — `/home/user/career-ops/AGENTS.md` (Ethical Use). "**CRITICAL RULE: Career-Ops never submits.**... You always click Submit." On Lever, the agent "never touches the checkboxes, the radio buttons, or the captcha" — `/home/user/career-ops/docs/APPLY_AUTOFILL.md`
- Code: `web/src/lib/apply/submit-guard.mjs` states "NEVER-SUBMIT is by construction for the planner's ACTION VOCABULARY... there is no 'submit' action to issue, a control this guard recognises as a submit control is listed with no ref so it cannot be named". It also admits: "an allowed control's own JS handler can still call `form.submit()`/`requestSubmit()`... No DOM heuristic closes that" — `/home/user/career-ops/web/src/lib/apply/submit-guard.mjs` lines 1–29
- A grep of non-test `.mjs` code for click/submit calls found only the guarded web apply driver (`web/src/lib/apply/drive-action.mjs`) and `scan-interamt.mjs` (clicking a search button on the German public-sector job portal scanner, not an application) — `grep` in `/home/user/career-ops`
- `apply-scope.mjs` refuses launch args matching `remote-debugging|user-data-dir|DevToolsActivePort|devtools`. AGENTS.md forbids attaching to the user's own Chrome via CDP — `/home/user/career-ops/apply-scope.mjs` lines 15–17; `/home/user/career-ops/AGENTS.md` (Apply scope)
- LinkedIn guard: one browser attempt per posting per run; "Do not retry LinkedIn through WebFetch, guest endpoints, alternate accounts, or anti-bot/login workarounds"; "does not authorize scraping or bypassing access restrictions" — `/home/user/career-ops/AGENTS.md` (LinkedIn JD loading guard #4121)
- LinkedIn in code: `liveness-api.mjs` calls `https://www.linkedin.com/jobs-guest/jobs/api/jobPosting/{id}`, described as returning "the rendered posting as HTML with no auth and no browser". It is "unauthenticated and rate-limited", with `throttleMs: 3_500` — `/home/user/career-ops/liveness-api.mjs` lines 27, 345–378; `/home/user/career-ops/lib/linkedin-url.mjs` line 63
- Other LinkedIn features are offline or draft-only: `linkedin-join.mjs` reads the user's own exported `Connections.csv` ("zero-token, offline, read-only"); `contacto` drafts outreach messages within LinkedIn character limits. It does not send them — `/home/user/career-ops/AGENTS.md` (Main Files; Skill Modes)
- Aggregator listings (LinkedIn/Wellfound/etc.) are "UNCONFIRMED by default" until found on the employer's own careers page or ATS — `/home/user/career-ops/AGENTS.md` (Aggregator Listings)
- The question of whether automated applications get candidates flagged was raised by users in the launch thread — [Reddit snapshot](https://reddit.sentinel-team.org/posts/1sd2f37/snapshots/2026-04-09T16%3A41%3A00.47446Z)

### Inferences
- Because no login cookies are used, the guest-endpoint liveness check cannot get the user's LinkedIn account banned. At worst the container's IP is rate-limited. It is still programmatic access to LinkedIn, which LinkedIn's terms generally discourage. Users who want zero LinkedIn automation can avoid running liveness checks on LinkedIn URLs and paste JDs instead.
- In a cloud session the auto-submit risk is effectively nil: headed form-filling cannot even launch (see §4).

### Gaps
- LinkedIn's current User Agreement text on guest-endpoint access was not fetched or quoted in this research.
- The proposed "independent interlock on the submit event", which would close the residual JS-handler submit gap, is documented as future work. No evidence was found that it has shipped.
